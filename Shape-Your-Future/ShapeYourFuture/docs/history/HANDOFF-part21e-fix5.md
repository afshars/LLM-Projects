# Part 21e fix 5: getPlanningProposal coverage issue
Decision (mine; you can overturn it): KEEP `apiClient.getPlanningProposal` and document it as intentionally unused. Reasons: every create/accept/edit/reject answer already returns the full proposal; `POST /planning-proposals` creates-or-refreshes the open one; proposal ids are not persisted across reloads, so there is no screen state a read-by-id would restore. Wiring it would mean inventing UI or store behaviour nobody asked for; deleting it would drop a tested contract for a real endpoint (`smoke/api-planning-proposals.test.ts`).
The only genuine use I found, NOT built: after a 409 ("no longer open") or a network error on accept/edit/reject, GET the proposal to show its real status instead of a retry that can never succeed. Say if you want it (small, in state/planning-proposal.ts `perform`).
