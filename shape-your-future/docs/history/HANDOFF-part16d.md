2. **Does detect SAVE? YES.** `POST /behavior/patterns/detect` -> `detect_patterns()` upserts one `BehaviorPattern` row per `pattern_type` and commits, then returns only the patterns that clear their thresholds in THIS scan. It never deletes: a saved pattern that no longer clears its threshold stays in `GET /behavior/patterns`. So the POST answer can hold fewer rows than GET. The flow therefore calls `invalidatePatterns()` after a successful POST and the tab reads GET again (the POST body is NOT put into the slice). Also on the server: `GET /behavior/patterns` with an empty cache runs detection itself (a write on a GET), and `?recompute=true` is the same as POST (not used here). **Backend wart to decide:** a stale pattern can stay listed and the UI cannot tell. `detected_at` is in the contract but not shown (not in the brief); say if you want "Detected on <date>" on the card.
3. **Contract, read from the backend, differs from the brief:**
   - `evidence` is a DICT (different keys per `pattern_type`), not a list. `evidenceEntries()` flattens it to one line per key ("Label: value"); a real list (the shape of `TaskFailureOut.evidence`) also works; null, undefined, NaN, blank and nested objects are dropped.
   - `description` is written by the server and is ALWAYS Persian (it can contain raw codes like «social_media», «LOW_ENERGY»). It is shown as it is, `dir="auto"`; in the English UI that sentence stays Persian. Everything around it is localized.
   - ADDITION (not in the brief, easy to remove): each card has a localized heading from `pattern_type` (5 labels, `patterns.types`), because the description cannot be translated. Evidence labels are per type (`patterns.evidence`); ratio shows as %, hours as a clock, `top_type` / `reason` as the existing 16b/16c labels, `avg_energy` as "x of 10". An unknown type or key is shown humanized ("late_night_scrolling" -> "Late night scrolling"), never hidden.
4. **Threshold: `MIN_PATTERN_SAMPLE = 3`** in state/behavior-patterns.ts (`isSmallSample(sample)`: known and `< 3`). It mirrors `MIN_SAMPLES = 3` in app/services/behavior_analysis.py. The backend does not send it (no field, no endpoint), so it is copied: change both together. **Be aware:** every detector already requires >= 3, so against today's backend no row has `sample_size < 3` and the warning cannot fire in practice. It is wired and tested (a row with 2). If you want a visible caution for borderline data, raise the constant (for example 5): one line, no other change. An unknown `sample_size` (null) shows "Not recorded" and makes NO warning claim. The same constant feeds the empty state ("at least 3 records").
