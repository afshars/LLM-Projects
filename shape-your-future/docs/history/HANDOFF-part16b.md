2. **Contract, read from the backend, differs from the brief:**
   - The date key is `occurred_on` (ISO `YYYY-MM-DD`), NOT `date`.
   - `task_id`: integer or null. `duration`: integer minutes, must be > 0. `energy_level`: integer, 1..10 (400 otherwise). All optional.
   - `status`: a plain `str` in the schema, default `"failed"`, NOT validated by the server. The only documented values are the model comment `failed | skipped | partial`; the form sends only those three. If the backend later enforces a list, `FAILURE_STATUSES` is the one place to change.
   - Analyze returns `{ task_failure_id, reason, confidence, signals }`; `reason` is one of the 10 `FAILURE_REASONS`; `signals` are short ENGLISH technical strings from the server (shown as is in an `dir="ltr"` list, with an "in English" label for screen readers).
3. **Analyze storage behavior:** the SERVER writes the new `reason` / `reason_confidence` onto the failure row (`analyze_behavior` commits), but does NOT store `signals`; there is no GET for an analysis. So the UI keeps each answer in memory (`analysisStore`, keyed by failure id): it survives a language change and tab switches with no request, and is lost on page reload or when the user reaches the login step. The list rows do not show `reason`, so the slice is not invalidated after an analyze. If a later part shows `reason` in the list, call `invalidateTaskFailures()` after a successful analyze.
4. **Rate limit:** the general limiter, `general_rate_limit_per_minute` = 60 per client address, on all three routes -> 429. Add and Analyze both go through `submitLock`: a 429 shows `errors.rateLimit` ("...Please wait a moment...") and keeps the button locked 3 s; a 429 on Analyze puts the previous analysis state back.
5. **Exported names.** `state/behavior-failures.ts`: `FAILURE_STATUSES`, `DEFAULT_FAILURE_STATUS`, `ENERGY_MIN/MAX`, `ENERGY_VALUES`, `isFailureStatus`, `isFailureReason`, `validateFailureForm`, `firstInvalidField`, `FAILURE_FORM_FIELDS`, `normalizeDigits`, `isIsoDate`, `todayIso`, `listFailures`, `numberOrNull`, `normalizeAnalysis`, `analysisStore` (`get/start/done/fail/restore/reset/subscribe`), `getFailureFormStatus/setFailureFormStatus/subscribeFailureFormStatus`; types `FailureFormValues/Result/Field/ErrorCode`, `FailureAnalysis`, `AnalysisEntry`. `state/behavior-failures-flow.ts`: `recordFailure(request)`, `analyzeFailure(id)`, `FAILURE_FIELD_PREFIX`. `views/behavior-failures.ts`: `createFailuresTab()` -> `{ node, update(slice, onRetry), focusForm(), dispose() }`.

(polite live region), focus back to the date, `invalidateTaskFailures()` (the list reloads at once). On error: `errorMessage(err, "save")` in a `role=alert` banner; typed values are kept.
