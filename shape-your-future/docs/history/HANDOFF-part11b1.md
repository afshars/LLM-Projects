# HANDOFF part 11b-1: state layer for edit + delete of Brain Dump items. NO UI, saves NOTHING.
- NEW `state/brain-dump-items.ts`: pure helpers, zero runtime imports (only `import type`). `validateScore(unknown)` (integer 0..100; reasons notNumber / notInteger / outOfRange), `validateItemPatch(patch)` (reports ALL bad fields at once), `updateItem(items, index, patch)` -> `{ok:true, items}` | `{ok:false, reason:"outOfRange"}` | `{ok:false, reason:"invalid", errors}`, `removeItem(items, index)`. Never mutate; untouched items stay the same objects; "nothing changed" / bad index in removeItem returns the SAME array (callers skip the redraw with `next === items`).
- Editable fields: `item` (trimmed, not empty), `type` (only task|worry|idea|obligation, no "other"), the four scores. `confidence` is the AI's and is never edited; other keys in a patch are ignored. A patch is all-or-nothing: one invalid field and nothing is applied.
- `state/brain-dump.ts`: new `items` in `BrainDumpState` = the WORKING copy of `result.items` (`result` stays exactly as the backend sent it). Plain state, so a view rebuild (language/theme change) keeps the edits and sends nothing. New `editItem(index, patch)` (returns the updateItem result, or `{ok:false, reason:"notReady"}`) and `deleteItem(index)` (boolean). Both work only in status "ready"; listeners are called only when something really changed.
- `items` lifecycle: null when idle / loading / error. A successful run starts a FRESH copy (old edits are NOT carried over). A 429 restores the screen with the edits. logout / `reset()` / 401 clear it.
- `BRAIN_DUMP_ITEM_TYPES` moved to `brain-dump-items.ts` (so that file stays import-free) and is re-exported from `state/brain-dump.ts`: no importer changes.
- The VIEW IS UNCHANGED: it still draws `result.items`. 11b-2 should draw `items` (fall back to nothing when null) and add the edit/delete UI.
- DECISIONS to check:
  1. Scores must be whole numbers. I did not have the `/confirm` request type in the zip; if the backend takes floats, relax `notInteger` in `validateScore`.
  2. Item text: only "not empty" is checked, no max length (unknown backend limit).
  3. Items are addressed by index (they have no id). After `deleteItem(i)` the later indexes shift down; the 11b-2 view must not keep an old index across a delete (and should decide where focus goes after one).
  4. Running "sort again" discards the edits, and so does a failed re-run (11a already drops the old result when a run starts). 11b-2 should ask before re-running when the user has edited anything.
